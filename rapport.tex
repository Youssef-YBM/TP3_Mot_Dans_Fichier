\section{Introduction}

Dans ce TP, j'ai écrit un programme qui lit un fichier \texttt{.txt}, demande un mot
à l'utilisateur et dit s'il y figure, sans tenir compte des majuscules.
Je l'ai fait de deux façons pour pouvoir comparer :
\begin{itemize}
  \item la version \textbf{STL}, qui s'appuie sur \texttt{std::string} et \texttt{find} ;
  \item la version \textbf{from scratch}, où j'ai écrit moi-même la boucle de recherche.
\end{itemize}
Le but est de mesurer ce que chacune coûte vraiment : j'ai chronométré
le programme avec \texttt{<chrono>}, rangé les mesures dans un \texttt{std::vector}
et utilisé \texttt{std::sort} et \texttt{std::accumulate} pour les statistiques.

Les fichiers du projet :
\texttt{recherche\_fichier\_string.cpp} (version STL),
\texttt{recherche\_fichier\_scratch.cpp} (version from scratch),
\texttt{benchmark.cpp} (comparaison des deux, sortie CSV) et
\texttt{texte.txt} (fichier de test, 130 lignes, 6\,711 octets).
Tout a été compilé avec g++ 16.2 (MinGW-w64) sous Windows 11, en C++17 avec \texttt{-O2}.

% ====================== 2 ======================
\section{Les deux versions}

\subsection{Version STL}
Le fichier est lu d'un coup via \texttt{rdbuf()} dans un \texttt{stringstream}.
Le texte et le mot sont mis en minuscules avec \texttt{std::transform}, puis
\texttt{find} renvoie la position de la première occurrence.

\begin{lstlisting}[caption={Recherche avec la STL.}]
size_t rechercher(const std::string& contenu, const std::string& mot) {
    std::string contenuLower = toLower(contenu);
    std::string motLower     = toLower(mot);
    return contenuLower.find(motLower);
}
\end{lstlisting}

\subsection{Version from scratch}
Ici le fichier est lu caractère par caractère avec \texttt{get()}. La recherche essaie
chaque position du texte et compare le motif lettre par lettre, en passant les deux
caractères en minuscules au moment de la comparaison. Il n'y a donc aucune copie du texte.

\begin{lstlisting}[caption={Recherche écrite à la main.}]
int rechercher(const std::string& texte, const std::string& motif) {
    if (motif.empty() || motif.size() > texte.size()) return -1;
    int n = (int)texte.size(), m = (int)motif.size();
    for (int i = 0; i <= n - m; ++i) {
        int j = 0;
        while (j < m && std::tolower((unsigned char)texte[i + j]) ==
                        std::tolower((unsigned char)motif[j]))
            ++j;
        if (j == m) return i;   // trouvé en i
    }
    return -1;
}
\end{lstlisting}

\subsection{Ce qu'on peut prévoir}
Avec $n$ la taille du texte et $m$ celle du mot : la version STL parcourt toujours tout
le texte pour le copier en minuscules, donc elle coûte $\Theta(n)$ même si le mot est au
tout début. La version naïve peut s'arrêter dès qu'elle trouve le mot ($O(m)$ au mieux),
mais elle coûte $O(n\cdot m)$ au pire.

% ====================== 3 ======================
\section{Comment j'ai mesuré}

Une petite fonction template chronomètre n'importe quel appel avec \texttt{steady\_clock},
qui est monotone et donc insensible aux changements d'heure du système.

\begin{lstlisting}[caption={Chronométrage d'un appel, en microsecondes.}]
template <typename Fonction>
double mesurerUs(Fonction f) {
    auto debut = Horloge::now();
    f();
    auto fin = Horloge::now();
    return std::chrono::duration<double, std::micro>(fin - debut).count();
}
\end{lstlisting}

Une seule mesure n'est pas fiable : un appel de quelques microsecondes est vite perturbé
par le système. Chaque cas est donc répété 200 fois, les durées vont dans un
\texttt{std::vector<double>}, puis je trie et je calcule min, médiane, moyenne,
écart-type et max. J'ai utilisé une variable \texttt{volatile} pour que le compilateur ne
supprime pas l'appel mesuré.

\begin{lstlisting}[caption={Collecte et analyse des temps.}]
std::vector<double> temps;
for (int i = 0; i < repetitions; ++i)
    temps.push_back(mesurerUs([&]{ sink = rechercher(contenu, mot); }));
std::sort(temps.begin(), temps.end());
double moyenne = std::accumulate(temps.begin(), temps.end(), 0.0) / temps.size();
double mediane = temps[temps.size() / 2];
\end{lstlisting}

Le protocole : le fichier de base est répliqué $\times 1$, $\times 10$, $\times 100$ puis
$\times 1000$ (jusqu'à environ 6,7 Mo), et je cherche trois mots :
\og Bonjour \fg{} (au début), \og Fin du fichier de test \fg{} (à la fin de la première copie)
et \og zzzxyz \fg{} (absent, donc parcours complet).

\section{Résultats}

la position 118. Pour la version from scratch, la recherche prend environ 0,8~$\mu$s

\section{Analyse}

\paragraph{Une croissance linéaire.}
Quand le mot est absent, les deux courbes de la figure \ref{fig:perf} sont des droites de
pente 1 : le texte est 10 fois plus grand, le temps l'est à peu près aussi. C'est bien du $O(n)$.

\paragraph{Mot au début : la version from scratch gagne largement.}
Elle s'arrête à la première occurrence, soit environ 0,1~$\mu$s quelle que soit la taille.
La version STL reste proportionnelle à $n$ parce qu'elle recopie et convertit tout le texte
avant même de chercher. Sur 6,7~Mo, l'écart dépasse cinq ordres de grandeur.

\paragraph{Mot absent : la STL gagne.}
Elle est environ 1,8 à 2,1 fois plus rapide, car \texttt{find} est très optimisé, alors
que ma boucle appelle \texttt{tolower} deux fois à chaque comparaison.
Ce que j'ai trouvé surprenant, c'est que le coût de la version STL vient surtout de la
copie en minuscules, et non de la recherche elle-même.

\paragraph{Variabilité.}
Sur les gros fichiers, l'écart-type devient important (6\,706~$\mu$s pour la STL sur 6,7~Mo,
mot absent) à cause du cache, des allocations mémoire et de l'ordonnanceur. C'est pourquoi
je compare les médianes plutôt que les moyennes.

\paragraph{Limites.}
La mise en minuscules ne gère que l'ASCII, donc pas les accents en UTF-8. Le mot \og fin \fg{}
est trouvé dans la première copie du texte répliqué, ce qui explique ses temps constants
en version from scratch. Enfin, les valeurs absolues dépendent de ma machine ; ce sont les
comparaisons entre versions qui comptent.

% ====================== 6 ======================
\section{Conclusion}

Aucune des deux versions n'est la meilleure dans tous les cas. La version from scratch
est imbattable quand le mot est proche du début, mais environ deux fois plus lente que la STL
dans le pire cas. La version STL a un coût stable de $\Theta(n)$ dû à la copie du texte.
Ce TP m'a surtout montré qu'il faut mesurer, avec des répétitions et la médiane,
avant de conclure qu'une implémentation est plus rapide qu'une autre.
